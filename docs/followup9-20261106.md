## SocketCAN application

Original native/socketcan_demo.c cross-built against real QNX SDP 8.0 with qcc -Vgcc_ntox86_64 -g -Wall -Wextra -Werror, external public SocketCAN headers and -lsocket. Final source (corrected standard-data filter) compiled successfully. No external implementation/header/binary is committed.

Linux cc -std=c11 -Wall -Wextra -Werror -O2 passed. Five demo tests passed, including real vcan1 RX 100/100 byte-exact and independently received TX 100/100 byte-exact, plus deliberate wrong-payload failure. Initial test exposed an incorrect CAN_ERR_FLAG filter mask; corrected before delivery. Full host suite: 96 tests, 4 explicit skips (native live demo separately opted in and passed). Redistribution guard passed.

TX_ACCEPTED in the application means writes accepted, not peer delivery; the live test separately receives and compares all 100 frames. This is Linux SocketCAN evidence. On-QNX SocketCAN runtime remains blocked by the module/board path; the cross-build does not resolve its ABI.

See socketcan-demo.md for build and run prerequisites. Demo is finite, classic CAN only and does not install or change a stack/service.

## Fresh QNX fallback traffic and SSH

The instrumented EDU image booted using max CPU under 100% host CPU / 1GiB memory cap, 1 vCPU, 512MiB guest RAM. In the same run, native libcan fallback observed 100/100 RX byte-exact and the host independently captured 100/100 TX byte-exact. PIRQ-to-IRQ10 correction, 30ms pacing and settling remain experimental requirements. These are NOT results from the SocketCAN demo.

sshd config and daemon start both returned zero with the existing OPENSSL_ia32cap=0 and SshdAuthPath workaround. The fresh host ssh-keyscan returned exit1, zero host-key rows. Therefore the prior successful handshake was NOT revalidated, authenticated login is still unverified, and the underlying memory fault is not fixed. No authentication policy was changed.

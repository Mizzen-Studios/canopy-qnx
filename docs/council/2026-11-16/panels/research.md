## Evidence-backed scorecards (editorial, not official criteria)

### HostShare — strongest low-level utility positioning
- **Distinctiveness: credible QNX-specific integration; generic idea established.** S1/S2 already solve host-folder sharing for other guests, and S3 is an existing QNX networked-file workflow. Pitch the QNX8 read-only virtio-9p resource manager and development friction it removes, not novel shared folders, novel read-only exports, or “first QNX driver.”
- **Technical support: strongest concrete device-to-user workflow of the three.** README:9–19 and docs/CURRENT_CONTRACT.md:9–18 state default IRQ11, mounted list/read, seven independent checksums, denied writes, live host edit and scoped remount. Current-contract:13–15 explicitly says pending-read kill occurs **before RPC/DMA**; this is not in-flight DMA safety.
- **Product gap:** native/hostshare_mount.h:26–40 contains useful read-only/path/type checks, but a seven-file success corpus is not broad filesystem conformance. docs/C_CORE.md:12–33 is a historical host-core boundary with concurrency/state limitations, not a current-driver failure finding. Do not collapse it into current acceptance. README:64–70 openly explains the historical EIO-only runner mismatch.
- **Highest-upside substantive change:** a **read-only developer-workflow conformance pack**: POSIX-style offsets/partial reads/EOF, directory pagination, file replacement/truncation between opens, two-reader correctness and deliberate rejection cases, with independently computed expected bytes. Extend supported implementation only where observed failures justify it. This makes a narrow port useful rather than merely demonstrable.
- **Ambitious option:** complete active-request cancellation/reset and safe teardown/re-attach during genuinely submitted DMA. **NEEDS OLLY APPROVAL**; high low-level upside, high DMA/lifecycle risk, native validation mandatory. Not recommended before basic conformance.
- **Recommendation:** prioritize conformance and reproducible no-network edit/read workflow. Retain read-only scope; do not chase write support, virtio-fs pivot or MSI-X badges merely to look broader.

### EDU — strongest distinct tutorial proposition, proof-of-learning gap
- **Distinctiveness: pedagogy and QNX translation, not the device.** S4 already supplies educational factorial/IRQ/DMA; S5 teaches QNX resource managers. EDU's genuine contribution is learner-owned predict/edit/diagnose/explain and **wrong FAIL despite app exit0**, followed by normal /dev/edu use, not inventing a PCI training device.
- **Technical support:** README:8–18 records one coherent source-bound wrong/correct/finish journey, host/native separation, licensed prerequisites and no independent learner acceptance. README:44–55 describes the notebook and admits no human-validated tutorial. docs/register-evidence.md:7–20 correctly pins upstream QEMU v8.2.2 source and distinguishes distro binary identity.
- **Product gap:** automation/operator success is not evidence a new learner understands IRQ acknowledgment, PCI mapping or resource-manager errors. README:72–75 explicitly leaves clean-machine learner impact pending. Setup complexity can dominate the learning task (README:34–52).
- **Highest-upside substantive change:** add a **transfer challenge** after the existing walkthrough: a different intentionally plausible defect, with predict-before-run and explain-after evidence, tested by someone not involved in authoring. Start with a bounded wrong-register/ack or resource-manager offset task selected only after API review; do not imply native coverage for an unrun branch. Independent completion with minimal intervention is the discriminator against ordinary copied driver labs.
- **Ambitious option:** an instructor-ready diagnostic fault curriculum with multiple selectable native faults, feedback tied to actual observations and independently assessed transfer. **NEEDS OLLY APPROVAL**; materially larger lesson and verification scope. Browser simulations must remain labeled non-QNX.
- **Recommendation:** one rigorously validated transfer exercise plus a genuinely independent learner study beats six more unvalidated chapters. A Linux-to-QNX concept comparison can reuse docs/learning-notes.md:43–51; it must not imply API compatibility.

### CANopy — compelling evidence workbench, narrow automotive value today
- **Distinctiveness: “what can this incident actually prove?”**, not CAN logging, restart, or safety. S6 already logs/replays CAN, S8 restarts processes and S9 reads logs. CANopy adds a bounded portable evidence pack, independent ordered post-restart traffic comparison, cited verdicts and UNKNOWN on insufficient input. docs/incident-pack.md:24–46 documents these distinctions and correctly denies attestation.
- **Technical support:** README:3–18 records fresh frozen-guest QNX SLM restart, new PID and exact100RX/100TX; guest_query current-source native runtime remains NOT_RUN. docs/native-recorder.md:42–48 records independent host capture and separate control; :67–72 denies timing and uninterrupted availability. This is concrete but not physical-vehicle evidence or target SocketCAN acceptance.
- **Product gap:** docs/incident-pack.md:46 accepts exactly one main kill and fixes recovery to100 frames/direction. This limits reuse for real engineering investigations. Current evidence is a bounded synthetic test exchange, not explanation of lost/corrupted vehicle signals. Do not invent semantic CAN/DBC coverage from historical host simulation (README:80–85).
- **Highest-upside substantive change:** a **loss-aware incident continuity analysis** using bounded sequence-numbered CAN traffic before/during/after restart: report observed missing/duplicate/out-of-order frames and explicit unknowable intervals, linked to raw streams. Existing independent host capture is a promising base; avoid claiming exact time-aligned outage or vehicle safety. Unlike another log viewer, it answers an automotive debug decision.
- **Ambitious option:** multi-incident comparative campaign with configurable expected traffic contracts and deterministic reproduction recipes, preserving separate run provenance. **NEEDS OLLY APPROVAL**; schema/query redesign and fresh QNX capture are substantial. Do not resume C6/actuation/heartbeat or claim a safety case.
- **Recommendation:** one observed sequence-gap report on the already-supported libcan/QEMU path before DBC/VSS integration, SocketCAN portability or new guest_query features. If authorization/caps prevent native capture, ship no new native headline; prioritize truth-preserving pack usability instead.
